# 문서 버전 관리 기준

이 프로젝트의 모든 문서(`project-overview.md`, `study-roadmap.md`, `curriculum.md`, `study-notes.md`, `case-studies.md`)에 공통 적용하는 버전 관리 규칙이다.

## 버전 시작 기준
프로젝트 초기 구축 단계(문서 틀을 처음 잡고 다듬어가던 과정)에서 있었던 세부 수정들은 개별 버전으로 추적하지 않는다. 모든 문서는 **v1.1을 공식 시작점**으로 삼아 이후 변경사항부터 버전 이력 표에 기록한다.

## 버전 표기 형식
`v{메이저}.{마이너}` 형식을 사용한다. 예: v1.1, v1.2, v2.0. 문서마다 독립적으로 버전을 관리한다 — 한 문서를 고쳤다고 다른 문서의 버전까지 같이 올리지 않는다.

## 버전을 올리는 기준

**메이저 버전 (+1, 마이너는 0으로 초기화)**
문서의 목표·범위·구조 자체가 근본적으로 바뀔 때 올린다.
- 프로젝트의 궁극적 목표나 방향이 변경될 때 (예: 화이트리스트/격리 기능의 접근 방식 자체가 바뀜)
- 로드맵의 단계 구성이 통째로 재설계될 때 (예: 개발 순서가 크게 뒤바뀜)
- 개발 방식의 큰 전환 (예: 완전 자체개발 → 오픈소스 전면 채택, 또는 그 반대)
- 문서를 처음부터 다시 쓰는 수준의 전면 개정

**마이너 버전 (+0.1)**
그 외 모든 수정은 마이너로 올린다.
- 보안 사례 신규 추가 (`case-studies.md`), 학습 기록 추가 (`study-notes.md`)
- 커리큘럼 주차/일정 조정, 추천 자료 추가·교체
- 환경/제약 조건의 세부 수치 변경 (예: 단말 규모, 인력 수 변경)
- 미결 사항 항목의 추가 또는 해결(완료 표시)
- 의미 있는 문장 수정이나 설명 보강
- 오탈자, 띄어쓰기, 표 서식 정리 등 자잘한 교정도 포함

## 수정 시 절차
1. 문서를 수정한다.
2. 위 기준에 따라 메이저/마이너 여부를 판단해 상단의 `**버전**: v{n}.{n} (날짜)`를 갱신한다.
3. 문서 하단 `## 버전 이력` 표에 새 행을 추가한다. 표는 아래 4개 열을 반드시 채운다.
   - **버전**: 갱신된 버전 번호
   - **날짜**: 수정일
   - **변경 위치**: 어느 절/항목이 바뀌었는지 (예: "1.3 환경 및 제약 조건", "사례 4 추가" 등 구체적으로)
   - **변경 내용**: 무엇을 왜 바꿨는지 한 줄 요약
4. 이전 버전 행은 지우지 않고 계속 누적한다. 이 표만 봐도 "언제, 어디를, 왜" 바꿨는지 전부 추적 가능해야 한다.

## Git 저장소 관리 규칙
이 프로젝트는 Private GitHub 저장소로 관리한다. 커밋 메시지에는 어떤 문서의 어떤 버전으로 바뀌었는지 명시한다 (예: `docs(case-studies): v1.1 -> v1.2, 사례 4 추가`). 문서 안의 "버전 이력" 표는 그대로 유지하고, git 커밋 이력과 이중으로 추적한다 — 문서만 열어봐도 이력을 알 수 있고, git log로도 실제 변경 diff를 볼 수 있도록 한다. 실제 비밀번호·API 키·사내 서버 IP 등 진짜 민감정보는 이 저장소가 private이더라도 절대 커밋하지 않는다.

## 종합 보고서(워드 파일)
종합 보고서는 이 저장소에 상시 보관·버전 관리하지 않는다. 필요할 때(예: 보고, 공유용) 그 시점의 문서 내용을 취합해 별도로 요청해서 생성하는 방식으로 운영하며, 저장소에는 올리지 않는다.
